    OT visibility in the platform
    
          
    Ensure your subnets are appropriately classified first. The OT zone adds subnets this capture has not
          used before (by default a Level-1 control net, a Level-0/field + building-automation net,
          and an industrial-DMZ net; the exact CIDRs are whatever you set above). Without that, OT devices fall into
          external / unknown, the devices do not classify into a zone, and the cross-zone and
          Purdue-violation events generated here will not read correctly in any platform.
    
          
    Why the zones matter. The Purdue model layers a plant so that each level only talks
          to its neighbours, and IT and OT meet in one controlled place. A conversation that jumps a
          boundary without passing through that place is the signal — segmentation is the core OT
          control, and the network is the only passive way to see it broken. Correct zone classification lets
          the platform label each side of a flow with its zone, so a violation is obvious.
    
          
    
            
    ZoneLevelWhat lives there
    
            
              
    IT / Enterprise5 / 4Business network — the user and server subnets, email, web, directory.
    
              
    Bridge — Industrial DMZ3.5The only place IT and OT meet: the jump host (the sole permitted initiator into OT), patch/AV relays, reverse proxy, a replicated read-only historian.
    
              
    OT — Operations3Site operations: SCADA, MES, historians, engineering workstations.
    
              
    OT — Supervisory2HMIs and line supervisory control.
    
              
    OT — Control1PLCs and RTUs — the controllers that run the process.
    
              
    OT — Process0Field devices: sensors and actuators, BACnet AHU/VAV/chillers, cameras, badge readers.
    
              
    Safety (SIS)—Isolated safety-instrumented controllers; written almost never. Any traffic to them is notable.

        What a replay does
        Replaying injects raw packets at a monitoring interface, so a sensor treats them as
        live traffic and will raise genuine-looking detections. The replay runs as a separate,
        detached process: it keeps going if this app closes unexpectedly, if you reload the page,
        or if the server restarts — reopen the app and it picks the replay back up.
        Quitting the app deliberately (Cmd-Q, Ctrl-C, or
        closing the launcher window) stops the replay, rather than leaving packets flowing
        with nothing watching. Closing only the browser tab does not: the app refuses to shut down
        while a replay is in progress. The monitor window can stop it at any time, with no
        password.

          Terms
          
        
          
          
          Scenario
          One piece of traffic with a purpose, such as a credential theft, a slow application or a weak certificate. Tick scenarios in Compose; each is placed on the capture day.
          
          
          Family
          The kind of scenario, shown as a coloured tag: SEC (security incidents), PERF (performance and availability faults), CRYP (crypto posture, such as weak TLS), REPLAY (replays of documented incidents) and CUSTOM (built from a recipe you add).
          
          
          Category
          A topic inside a family, for example Initial access, DNS and DHCP faults or Weak TLS. The category rail in Compose filters the list by category.
          
          
          Recipe
          A JSON description of a scenario, exported from a profiled pcap in Lab. Adding it makes the next build include one CUSTOM scenario that recreates that traffic in the simulated network.
          
          
          Campaign
          A short, staged story of network behaviour that you build from threat indicators in Campaigns. It adds traffic to the next capture only; nothing attacks anything.
          
          
          Capability module
          An add-on that adds a diagram, scenario, protocol or sensor provider. You can load and unload one without restarting. They are listed in Lab.
          
          
          Always-on feeds
          Background traffic that is part of the normal day and is listed in the chooser but cannot be switched off: the smart-board server, and the OT and IoT background when the OT zone is on.
          
          
          Baseline day
          The normal business traffic of the simulated company. It is always in the capture; scenarios are placed on top of it. Choosing no scenarios gives a clean baseline day.
          
          
          Scale
          How much traffic the baseline day holds. 1.00x is a full day (about 7 GB); smaller values give a quick sample with the same mix of protocols.
          
          
          Threat collection
          A STIX 2.1 bundle of the external indicators the capture actually emitted. Loading it into a sensor turns those flows into threat-intelligence matches.
          
          
          Decryption keys
          The server certificates and private keys written beside the capture. Load them into a sensor so it can decrypt the capture's HTTPS. Each build mints new ones, so they only fit the capture they came with.
